# Research cache and Git tracking

Git tracks the C++ and Pascal implementations, extraction/decompilation tools,
authored reviews, comparison policy, reviewed routine extents, translation
catalogs, and regression fixtures. Machine exports and reports stay local.

| Local, ignored path | Purpose |
|---|---|
| `data/` | Extracted maps, dialogue, campaign inputs and audit reports |
| `reference/original/decompiled/` | Gameplay Ghidra exports and indexes |
| `reference/original/presentation/decompiled/` | Presentation exports |
| `reference/original/presentation/*.json`, `published-methods.tsv`, `EVENTS.md` | Form and effect inventories |
| `reference/original/whole-program/` except `REVIEW.md` and `IDR-LICENSE.txt` | Assembly, analysis snapshots, manifests and generated ledgers |
| `reference/original/ui-extraction-manifest.json` | Extracted picture inventory |
| `reference/delphi2/*.json`, `runtime-spans/` | Compiler comparison reports and assembly excerpts |
| `cpp/locales/source/` | Raw Japanese and HTML5 extraction evidence |
| `build/` | Executables, dependencies, Ghidra projects, media and build reports |

Existing local copies were retained when these paths were removed from Git's
index. Fresh checkouts do not include them. Ordinary C++ builds and tests use
tracked constants, catalogs and fixtures; the Windows GUI also requires the
original installation's media. Research verification requires the cache below.

## Prepare data

From the repository root:

```powershell
python -m pip install -r tools/requirements.txt
python tools/prepare_research.py --source "D:/Program Files (x86)/Tower of the Sorcerer"
python tools/prepare_research.py --check
```

Preparation checks the supported English 1.2 executable, copies it into
`build/research/TSW.exe`, extracts maps/dialogue/media and form metadata, then
recovers events. A new campaign is assembled after event recovery. Existing
editable `campaign.json` and `interactions.json` are preserved. To deliberately
rebuild a campaign from the current events and interactions, run
`tools/extract_original.py --source ORIGINAL_DIRECTORY --regenerate-campaign`.

Optional audits are generated by the individual `tools/audit_original_*.py`
commands. Help extraction uses `tools/extract_help.py`; Japanese evidence uses
the commands in [the localization guide](../cpp/locales/README.md#reproduce-extraction-and-compilation).
Historical one-off notes such as `data/original-cycle-evidence.json` and
`data/event-ending-disassembly.txt` remain local; preparation does not claim to
recreate those old observations.

## Prepare decompilation

Use Ghidra 11.0.3 and its required Java runtime, then run:

```powershell
python tools/prepare_research.py --source ORIGINAL_DIRECTORY --decompile --ghidra GHIDRA_DIRECTORY
python tools/prepare_research.py --check --decompile
```

This explicitly regenerates exports and inventories at the paths above. It
creates a separate Ghidra project under `build/research/` and retains it for
inspection. It does not modify an existing analyst project. Preserve any
manually adjusted local exports before requesting regeneration. The IDR input
versions and download hashes live in `tools/idr-inputs.json`, so preparation does
not depend on an already-generated structural inventory.

The pipeline exports gameplay and presentation routines, snapshots discovery,
then iterates structural roots and whole-program recovery until the roots
stabilize. Accounting validates instruction bytes against the original EXE.
Fresh Ghidra analysis can produce different names, boundaries or unresolved
regions from a historical snapshot. A successful extraction is not a new review
or a claim of behavioral equivalence. The authored review documents describe
their original measured snapshots; they are not rewritten by preparation.

Delphi reconstruction remains a separate command:
`python tools/reconstruct_delphi_project.py`. Its generated includes remain
tracked as build inputs. Compiler preparation and generated compiler reports
are described in [the Delphi compiler guide](../reference/delphi2/README.md).

## Hash policy

Keep hashes when a check depends on the identity: supported original executables,
pinned third-party downloads, cached exports reused by Ghidra, and built binaries
or verification reports carried into packaging. These prevent using a different
program or associating results with the wrong build.

Do not store hashes merely to fingerprint every intermediate file. The routine
comparator uses tracked reviewed extents and decodes the original machine code
directly; it no longer pins assembly-listing whitespace or entire inventory JSON
files. Generated ledgers do not repeat the export manifest's hash table, and
presentation inventories do not add redundant source/assembly fingerprints.
Report freshness checks recompute their meaningful contents.

Generated C++ constants/localization and Delphi includes remain tracked until
their generators are part of the build. Test recordings and expected JSON are
stable regression inputs and remain tracked. No blanket `*.json` ignore applies.
